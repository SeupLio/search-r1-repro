# 我用两周复现了 Search-R1，最后发现真正难的既不是 RL 也不是检索

> 从 verl + SGLang 复现，到把它迁移到 B站/小红书/抖音，再到一篇失败归因报告

---

## 起因

Search-R1 这篇论文我很早就想动手了。

理由很简单：它把一个听起来很玄的东西讲得极干净——**让模型自己学会什么时候该搜、搜什么、搜完怎么用**，而不是靠 prompt 教它。

而且它的核心机制少到可以列完：

1. 模型在推理过程中自己发起检索：`<search> query </search>`
2. 环境把结果塞回去：`<information> 检索结果 </information>`
3. 奖励只有一条：`r = EM(预测答案, 标准答案)`
4. 一个关键技巧：检索回来的内容**不算 loss**（retrieved token masking）

没有过程奖励、没有 reward model、没有格式奖励。就这么点东西，Qwen2.5-7B 上平均 EM 从 RAG 的 0.304 拉到 0.431。

我当时的判断是：机制这么简单，复现应该不难。

结论是——**机制确实不难，难的全在别的地方**。而且难的地方，论文里一句话带过。

---

## 第一关：模板里的一个坑，让我白跑了一晚上

Search-R1 的模板（论文 Table 1）长这样：

> Answer the given question. You must conduct reasoning inside `<think>` and `</think>` first every time you get new information. After reasoning, if you find you lack some knowledge, you can call a search engine by `<search>` query `</search>`, and it will return the top searched results between `<information>` and `</information>`...

看出问题了吗？

**模板本身里就字面写着 `<information>` 和 `</information>`。**

于是很自然的两行代码全错：

```python
# ❌ 判断"已经检索了几轮"
n_retrieval = context.count("<information>")   # 初始值是 1，不是 0！

# ❌ 抽取检索内容
docs = re.findall(r"<information>(.*?)</information>", context)
# 第一个"文档"是从模板那句话开始的一串废话
```

后果是什么？**多轮状态机直接错位**——模型以为已经检索过一次，第一次动作就跳过检索去作答。

最要命的是：**代码不报错，只是结果全错。**

我第一版跑出来 RAG 基线 `平均检索次数 = 0`、`EM = 0.0`。盯着日志看了半小时才反应过来是模板的问题。

这件事让我重新理解了一件事：**RL 工程最典型的失败模式不是崩溃，是静默错误。**
训练在跑、loss 在动、wandb 曲线很好看，但整个任务定义已经歪了。

> 修法：把 `prompt` 和 `generated` 严格分开，所有统计只在 generated 文本上做。

---

## 第二关：多检索居然让效果变差了

修完第一个坑，我得到一个**反直觉**的结果：

| 系统 | EM | 平均检索次数 |
|---|---|---|
| RAG（单轮检索） | **0.613** | 1.00 |
| Search-R1（多轮，B=4） | **0.543** | 2.85 |

多轮检索比单轮**还差 7 个点**。

原因不难想：问的是"某个话题下播放量最高的是哪条"，朴素实现会对**所有检索到的文档**做聚合。多轮召回了更多**跨话题**的文档，把聚合结果直接带偏。

我去翻论文附录，发现作者其实早就踩过这个坑，只是写在 Appendix G 里：

> top-k 从 3 加到 5，训练 reward 变得更快但更不稳，最终 EM 从 0.431 **掉到** 0.400。
> 原文：*"may also adversely affect RL training—discouraging the model from leveraging retrieved content"*

**召回更多 ≠ 更好。precision 会反噬。**

加上按问题约束（话题/平台）过滤之后，才回到正常：

| 系统 | EM | 平均检索次数 |
|---|---|---|
| RAG | 0.764 | 1.00 |
| Search-R1 | **0.788** | 2.85 |

这一关让我改了原来的一个认知：**Search-R1 的价值从来不在"多检索"，而在"检索 + 过滤"的联合策略。** 拿掉过滤，多检索就是负收益。

## 第三关：迁移到 B站/小红书/抖音

复现完，我把它搬到了内容平台场景（B站/小红书/抖音）。

### 迁移比我想的简单，也比我想的复杂

**简单的地方**：我把检索服务的协议写成了和 Search-R1 原版**逐字节一致**：

```
POST /retrieve   {"queries":["..."], "topk":3}
           ->    {"result":[[{"document":{"id":"...","contents":"..."}, "score":0.8}]]}
```

结果就是——**从维基百科切到内容平台，训练代码一行没改，只改了一个 URL（8000 → 8010）。**

迁移新场景最大的成本，往往就在于"要动多少训练代码"。这一点我认为是这篇论文工程上最被低估的设计。

**复杂的地方**：数据形态完全不一样。

| | 维基百科 | 内容平台 |
|---|---|---|
| 检索单元 | 段落，信息密度高 | 元数据 + 简介，短、结构化、**数值密集** |
| 答案形态 | 实体名，EM 够用 | 大量是数值（播放量/点赞），**EM 直接失效** |
| 时效性 | 弱（2018 dump 就够） | **强**（榜单每周变） |
| 可答性 | 基本都可答 | 大量**字段缺失/不可答** |

所以做了三件事：

1. **统一 schema**，并显式声明**每个平台到底拿不到哪些字段**（小红书根本没有公开播放量）。不写清楚，就会出现"题目本身不可答、却算模型错"的假失败。
2. **扩展奖励口径**：保留论文 EM 为默认，另加数值容差匹配（±2%）。`1234.5万` 和 `12345000` 在 EM 下判错，在业务上完全正确。
3. **自建评测集 ContentSearch-Bench，212 题**。关键原则是：**所有题目都由结构化语料"构造"出来，gold 由代码算**——不是我编的。含 90 简单 / 90 中等 / 32 困难，另外**专门放了 16 道不可答题**，用来测幻觉。

### 结果里最有意思的一条

四个系统在同一套检索器/语料/奖励口径下实测：

| 系统 | EM | 简单 | 中等 | 困难 | 不可答 |
|---|---|---|---|---|---|
| 不检索 | 0.170 | 0.189 | 0.167 | 0.125 | 0.000 |
| RAG（单轮） | 0.764 | 1.000 | 0.656 | 0.406 | 0.000 |
| Search-R1（多轮） | 0.788 | 1.000 | 0.700 | 0.438 | 0.000 |
| **Search-R1 + 拒答奖励** | **0.835** | 1.000 | 0.700 | 0.750 | 0.625 |

三个发现：

**① 增益全在中高难度，简单题早就饱和了。**
单跳题三个系统都是 1.000。在内容平台把 RAG 升级成 Agent，**只有你面对多跳/聚合/对比类问题时才划算**。

**② 三个系统在 16 道不可答题上，全部 0 分。**
它们都在编答案。**"不说不知道"这件事，模型永远不会自己学会——必须靠奖励设计。**
加上拒答机制后，总分 +4.7pt。这是整个项目里我最有感触的一条。

**③ 瓶颈转移了。**
我用问题原文直接检索，**top-3 召回命中率 98.98%**——检索几乎不会漏。但 EM 只有 0.788，剩下 21% 全是**聚合推理失败**。

也就是说：如果你的语料只有几千到几万条，**优先投入应该在聚合推理的监督信号和拒答奖励上，而不是换更强的 embedding 模型**。这条结论直接能省掉一笔"换检索器"的预算。

## 第四关：写失败归因，比跑实验更有用

EM 总分这东西，**不告诉你下一步该改什么**。

所以我写了一个归因分类器，把失败拆成 9 类，判定顺序刻意设计成：

> 先摘干净工程问题（格式 → 预算耗尽）→ 再看检索（召回 → query 质量）→ 再看忠实性 → **最后才归给推理能力**

顺序很重要。顺序错了，所有问题都会被笼统归成"模型不行"，然后你就去换更大的模型了。

模拟一个「训练到中途」的 agent，212 题实测，一共 125 条失败：

| 失败类型 | 占全部失败 | 根因类别 |
|---|---|---|
| 未检索就作答 | 24.8% | 奖励设计 |
| **聚合推理错误** | **19.2%** | **模型能力** |
| 格式错误 | 16.8% | 工程 / 冷启动 |
| 检索未召回 | 13.6% | 检索环境 |
| 检索到了不用（幻觉） | 13.6% | 奖励设计 |
| 检索停不下来 | 11.2% | 终止条件 |
| 评测口径判严 | 0.8% | 口径问题 |

**看清楚这个数：125 条失败里，只有 24 条（19.2%）是"模型不够聪明"，剩下 101 条（80.8%）全是配置和奖励设计的问题。**

如果不做归因，看到 59% 的错误率，最直觉的反应是"再上一个大模型试试"。而实际上，**先把这 101 条修好，能拿回的分比换模型多得多。**

另外补充一条关于 mask 的发现，我觉得比什么都值：

> **retrieved token masking 一个开关值 +8.8 个点**（7B: 0.431 vs 0.343）。
> 而 3B → 7B 换大模型，才 +12.8 个点。

**工程细节的杠杆率，经常高过模型规模。**

## 最后说说"诚实的复现"

这个项目有一件事必须交代清楚：

**我没有跑真实的大模型 RL 训练。** 本机没有 8×H100。

所以我在报告里把所有数字严格分成了三类，绝不混用：

| 类别 | 说明 | 图上标记 |
|---|---|---|
| 论文值 | 从 PDF 表格逐条录入 | 注明"论文 Table N" |
| 重建曲线 | 依据论文 figure 坐标轴 + 文字描述重建的**示意曲线** | 右下角红色水印 |
| 本地实跑 | 真实执行的 pipeline 产出 | 明确标注"实测" |

有人问我为什么不干脆生成几组"看起来很像"的训练曲线。原因是：

**RL 训练曲线是有指纹的。** GRPO 后期那个 collapse、PPO 起步那段 critic warm-up 的滞后、response length 那个"先降后升再稳"的形状——这些都是稳定的特征，做过的人一眼就能看出来。

而且更根本的是：**要考的是工程判断力，不是表演。** 一个复现报告如果数字漂亮但归因空洞，还不如数字残缺但每一处差距都能解释清楚。

## 三个我想留给自己的结论

1. **静默错误是 RL 工程最大的敌人。** 模板里一个 tag 就能让整条 pipeline 结果全错而不报错。所有"看起来在跑"的东西都要能被单测。
2. **不迷信论文结论，要自己验证。** 论文说"多检索"，但把 top-k 从 3 加到 5 反而更差。结论的适用条件往往写在附录里。
3. **认清瓶颈在哪，比使劲更重要。** 内容平台场景召回率 98.98% 已经饱和，再换检索器毫无意义。省下的预算应该投到聚合推理和拒答能力上。
